# 开口规则工作台实现说明

## 本次目标

把开口规则从“前端占位”推进到“后端可读、可写、可参与生成”的状态，并逐步收紧规则模型，避免一开始把问题做得太宽。

本次实现围绕三件事展开：

1. 先去掉 `Top / Bottom` 这类过早引入的层维度。
2. 只保留 `package + padType` 作为当前可用的规则匹配维度。
3. 让规则不仅能导入导出，还能参与焊盘分组和生成结果。

## 为什么先这样做

开口规则工作台最容易失控的地方，不是“能不能编辑”，而是“维度是不是一开始就太多”。

我们先把模型收窄到：

- `package`
- `padType`

这样有几个好处：

- 用户更容易理解规则在匹配什么。
- 后端逻辑更容易稳定下来。
- UI 不需要同时承载太多工艺概念。
- 后续如果真的需要继续细分，还能在这个基础上加回去。

`Top / Bottom` 先不作为当前判断维度，是为了避免把 PCB 的正反面问题和当前的规则生成目标混在一起。

## 已实现内容

### 1. 规则按 `package + padType` 匹配

现在工作台的规则匹配逻辑会优先使用：

- 封装类型 `package`
- 焊盘类型 `padType`

`layer` 已经不再参与当前规则匹配。

对应实现主要在：

- `src/stencilforge/aperture_workspace.py`
- `src/stencilforge/pipeline/core.py`

### 2. 规则会进入生成流程

规则不再只是 UI 预览，而是会参与开口推导与生成结果。

目前支持的规则动作包括：

- `delta`
- `scale`

生成流程会读取当前工作台状态，再把匹配到的规则效果带入最终结果。

### 3. 规则分组已经可见

为了让用户更容易理解“当前规则到底归到哪一组”，后端新增了分组导出能力。

分组逻辑现在按：

- `package`
- `padType`

来聚合规则。

这样做的目的不是单独做一层新的业务概念，而是让：

- UI 能显示规则组摘要
- 后端能记录当前匹配落点
- 生成日志更容易追踪

### 4. 导入 / 导出保持兼容

规则工作台现在支持：

- JSON 导入
- JSON 导出
- 旧字段别名兼容
- schema 版本检查

导入时会忽略不再使用的字段，比如旧的 `layer` 维度。

### 5. 回归测试已经补上

目前测试覆盖了：

- 默认工作台是否有可选规则
- 规则摘要是否可读
- `package + padType` 的匹配优先级
- 旧字段别名是否还能导入
- 旧的 `layer` 是否被正确忽略
- 规则导入 / 导出是否能往返
- 规则分组摘要是否正确生成

## 当前结果

这条线现在已经从“UI 占位”推进到了“后端可用”：

- 规则能编辑
- 规则能导入导出
- 规则能参与生成
- 规则能按 `package + padType` 分组展示
- 规则组还能作为规则列表的筛选入口
- 规则组选中态会随工作台状态一起保存和恢复

## 后续可以继续做什么

下一步比较自然的方向是：

1. 继续细化焊盘分组生成的显示方式。
2. 增强规则和实际几何生成的映射说明。
3. 如果以后确实需要，再评估是否把 `layer` 重新作为可选维度加回来。
